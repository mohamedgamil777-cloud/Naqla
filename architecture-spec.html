01

Recommended product architecture

One codebase, one database, three surfaces that share the same server-side truth. The customer never computes a price or an availability — the server does, every time. This is the single most important architectural decision, because it kills the two failure modes that would break the business: double bookings and price tampering.

🛻 Customer PWA

Installable mobile web app. RTL, huge buttons, 8-screen booking wizard, OTP login, my-bookings. Works offline-tolerant, no app-store friction.

🖥️ Admin dashboard

Responsive (desktop → mobile). Fleet, live availability board, bookings, drivers, pricing, reports, settings. Role-gated.

⚙️ Shared core

One API + one Postgres. Availability engine, pricing engine, notification & payment abstraction layers. All business rules live here — never in the client.

Notification abstraction

A single NotificationProvider interface. MVP uses a no-op/log adapter; SMS, WhatsApp Cloud API, and Web Push are drop-in adapters added later without touching booking code.

Payment abstraction

A single PaymentProvider interface. MVP records cash/manual payments; Paymob / Fawry adapters plug in for Phase 3 with no changes to invoicing.

Recommendation: a single Next.js app with route groups (customer) and (admin) over one Supabase Postgres. Not microservices — that would be over-engineering for an MVP and would make the availability engine (which must be transactional) harder, not easier.

Admin user flow

Daily operating loop

  1. Open Dashboard → today's bookings, active rentals, revenue in one glance.
  2. Open Board → see the whole fleet's hour grid; spot gaps and clashes.
  3. Handle incoming bookings → confirm / assign vehicle / assign driver.
  4. At pickup → Handover: fuel, mileage, damage photos, customer confirms.
  5. At return → record mileage/fuel/new damage → generate final invoice, settle deposit.

Board-driven booking (walk-ins)

  1. Click an empty slot on the availability board.
  2. Choose: Create booking · Block time · Maintenance · View.
  3. Enter customer name + phone → duration auto-fills from the slot.
  4. Price computed server-side → record cash/deposit → done.

The same availability engine serves customer app and admin — one source of truth, no divergence.

The double-booking guarantee (the important part)

Overlap prevention is not application logic that can be raced — it's a database constraint. Two customers clicking "confirm" on the same slot at the same millisecond: only one row commits, the other gets a constraint violation the app translates to العربية مش متاحة.

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
     vehicle_id WITH =,
     period     WITH &&          -- ranges overlap
  ) WHERE (status IN ('pending','confirmed','ready','active'));

-- vehicle_blocks (maintenance) shares the same idea, so a car in
-- maintenance is un-bookable for the same structural reason.
Why tstzrange + EXCLUDE: it makes the strongest correctness requirement in the whole spec (test cases 52) impossible to violate, even under concurrency, retries, or buggy client code. Buffer time is handled by padding the range on write.

Every write path is idempotent and re-validated. POST /bookings carries an idempotency key (double-click safe), re-runs the quote, and relies on the EXCLUDE constraint as the final gate. The client price is only ever compared, never trusted.
08

Availability / booking logic

A pure, testable engine. Given a vehicle and a day, it produces the hour grid; given a start, it produces valid durations; given a request, it either books or explains why not and offers alternatives.

Slot generation inputs

  • Branch working hours for that weekday (e.g. 08:00–22:00).
  • Existing bookings (active statuses) and vehicle_blocks (maintenance/blocks).
  • Buffer time between rentals (padding on each side).
  • Min / max rental duration and configured duration options.
  • Vehicle status — inactive/maintenance ⇒ no slots at all.
  • Advance-booking window and "الآن" lead-time (can't book 5 minutes ago).

Example — Pickup 01, Sat 20 Sep

الوقت08–0909–1010–1111–1212–1313–1414–15
الحالة متاح متاح محجوز محجوز متاح متاح متاح

Customer picks 10:00 → engine offers only ساعة (10–11 is booked, so 2h/4h/8h are hidden). Picks 12:00 → offers ساعة / ساعتين (up to the next block).

Booking transaction (race-proof)

BEGIN;
  -- 1. re-quote server-side from pricing_rules (ignore client price)
  -- 2. build padded range:  [start - buffer , end + buffer)
  INSERT INTO bookings (vehicle_id, period, status, price_snapshot, ...)
  VALUES (:v, tstzrange(:start,:end,'[)'), 'pending', :quote, ...);
  -- EXCLUDE constraint fires here if anything overlaps → rollback
COMMIT;

On violation the app returns, not an exception, but: العربية غير متاحة في الوقت ده + أقرب مواعيد متاحة computed from the same grid.

Adjacent bookings & the buffer

Existing 10:00–14:00, new request 14:00–16:00: allowed only if buffer_min = 0. With a 30-min buffer, the earliest adjacent start becomes 14:30. This is a single setting — see decisions.

09

Pricing logic

Layered and fully server-side. The engine takes vehicle + period + options + promo, resolves the applicable rule (vehicle → category → global), and returns an itemized breakdown that the UI simply renders. Nothing is hidden.

Resolution order

  1. Base rate — pick the best-fit hour tier (1h, 2h, 4h, 8h) or the daily cap for long rentals.
  2. Multipliers — weekend / peak-hour / holiday, applied to the base.
  3. Add-ons — driver fee, delivery/pickup fee.
  4. Discounts — promo code (validated: dates, min value, scope, uses).
  5. Tax/VAT — if enabled in settings.
  6. Deposit — shown separately, refundable.

Worked example — Van + سائق + توصيل

Deposit (e.g. 500 جنيه) is displayed under the total, clearly marked refundable.

Anti-tampering: the /quote endpoint is the only source of prices. At booking time the server recomputes and stores an immutable price_snapshot — so later rule changes never alter a confirmed booking, and a hacked client price is simply overwritten.

Decisions that need your call

Each has my recommended default so you can approve the whole set with one "yes", or override individually. These are business decisions, not technical ones — but they shape the build.

1 · Login timing. Should customers see prices before logging in? Default Yes — browse & see price freely; OTP only at "تأكيد الحجز". Fewer drop-offs.
2 · Buffer between rentals. Default 30 minutes (cleaning/refuel/return). Adjacent same-minute bookings therefore not allowed. Configurable.
3 · Minimum rental. Default 2 hours (spec lists 1h durations, but a 1-hour van rental is rarely worth the ops overhead). Easy to set to 1h.
4 · Daily pricing. Default engine charges the cheaper of summed hour-tiers vs the daily rate — customer always gets the best price automatically.
5 · Advance booking window. Default book up to 30 days ahead, and "الآن" means the next slot ≥ 1 hour from now.
6 · Cancellation policy. Default free until 6 hours before pickup; after that, deposit may be held. Fully configurable text + rule.
7 · Deposit. Default enabled, cash on handover, recorded manually in MVP; online hold arrives with payments in Phase 3.
8 · Number display. Recommend Western digits (0–9) for prices/times — measurably more readable for the target users, even in Arabic UI.
9 · OTP channel. Default SMS in MVP via a pluggable gateway; add WhatsApp OTP (cheaper) in Phase 3. Which SMS provider do you use today?
10 · Launch branch(es). Default build multi-branch, launch with one. I need: branch name, address, working hours.
11 · Seed fleet. To build something real (not mockups), I need your actual vehicles — or I'll seed realistic sample data (2 pickups, 2 vans) you replace later. Recommend the latter to start.
12 · Payments in MVP. Default cash / manual only; Paymob or Fawry later. Confirm which gateway you'll want so I shape the adapter.
